## Verdict — is the R-1 additivity check satisfied?

If `full-move` measured the same scene as `entity-service-only` + `render-update-only`, the two parts must add up to the whole. The `residual` column is `full - (service + render)`; a value near zero means the phases are additive and the rows are comparable.

Reading the residual column: in the product mode it stays inside ±6 % from 10k to 100k, which is what R-1 asked for — the two phases of one command add up, so the scene really is shared. Two rows deviate and both for measurement reasons, not fixture reasons: n = 1000 is the smoke run (cold JIT, kept only because it is the first record the builder ever produced) and `per-entity` at 50k pays a different amount of GC in the render-only pass (595 MB heap Δ) than inside the full pass. Treat the `per-entity` rows as upper bounds, not as precise deltas.

## Largest size in one transaction

n = 100000 MOVE ran as **one** `startUndoMark` / `startTransaction` / `commitTransaction` / `endUndoMark` sequence (one user command, one undo boundary), not as split transactions. The synchronous part is **3.61s**; undo is **1.53s**, redo **1.56s**, heap Δ **385.25MB**, process high-water **1866.63MB**.

## Reading the numbers

- `tx modify` = open-for-write + `transformBy` + `recordModify` snapshot; `tx commit` = `finalize` (after-snapshots), event dispatch and undo record.
- `old geometry removal` / `re-conversion` are the view phases; in the product they run through `AcTrEntityUpdateQueue` after the commit, so the blocking part of a MOVE is `tx modify + tx commit` and the rest is spread over later frames.
- `optimize()` is the batched-container re-pack. A per-layer material mode turns n entity updates into one re-pack per layer; `per-entity` cannot.
- `heap Δ` is a `heapUsed` delta for the measured pass and `max RSS` is the process high-water mark. Neither is a peak-heap measurement.
